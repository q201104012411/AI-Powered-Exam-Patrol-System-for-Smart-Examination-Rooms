## 1. 需求①：局域网链路 + 03 终端"清空"

### 1.1 先澄清"03 无法清空"的两个真正原因（都不是权限问题）

| # | 原因 | 证据 |
| --- | --- | --- |
| A | **GUI 里根本没有"清空远端记录"的功能**。`prune_remote()` 只是"超过上限自动裁最旧"的内部兜底，用户看到的现象就是"收到了但清不掉" | `storage.py` 全文检索 `purge`：改造前为 0 命中 |
| B | 原来那个「清空本地数据」按钮**直接删 `.db` 文件**。终端正在运行，SQLite 连接持有 `terminal.db` 句柄 ⇒ **必然 `WinError 32 另一个程序正在使用此文件`**；而且它**先把动作写进审计、再删文件**，于是"没清掉还留了痕" | `main.py` 自检旧输出：`已清除：attachments, outbox；失败：terminal.db:[WinError 32]` |

### 1.2 修完之后

| 能力 | 实现 |
| --- | --- |
| 4 个清空范围 | 远端记录 / 本机告警与复核留痕 / 补传队列 / 全部 |
| 2 种模式 | `mark`（标记，数据仍在、可审计）/ `hard`（真删，**仅所有者**） |
| 留痕 | 每次清空写 `audit` 哈希链 + 新增 `purge_log` 表（谁/何时/范围/条数/原因） |
| 强制填原因 | 原因必填，未填直接拒绝执行 |
| **不删库文件** | 改为库内事务清理，运行中也能真正清干净 |

新增「数据维护」页签（不必再翻到"运行状态与管控"里找按钮）。

### 1.3 顺带揪出的**第二处**同源缺陷（这是原报错的真正来源）

`fleet.execute_wipe()`（远程擦除）**也在删 `config.DB_PATH`**，报的正是用户截图那条错。
更严重的是：**自检里那条断言只检查消息里有没有"失败"两个字**，所以它长期"通过"却其实没清掉 ——
典型"测试太宽松掩盖了缺陷"。

已改为走 `storage.purge_data`，并把断言收紧成 4 条硬断言：

```
PASS 擦除不删除数据库文件（WinError 32 的根因）
PASS 擦除后告警确实被清空（不只是报了个成功）　— 擦除前 4 条
PASS 擦除后审计链仍完整（留痕可追溯）　— 审计链完整（26 条）
PASS 擦除不销毁终端账户
```

## 2. 需求②：13 融入 02 + 智能终端"发布命令"

### 2.1 融入方式（为什么不是直接 import 13）

各模块**都有同名的 `config.py` / `models.py`**，同进程 import 必然互相覆盖 ——
这也是本项目一直用"子进程 + JSON"的原因。所以把 13 的检测核心**合并成一个自包含模块**：

```
13\detect.py + 13\detector.py  ->  02\fire_detect.py（1115 行，无外部依赖）
   · config.load_settings() / config.onnx_model_path()  -> 内联（31 个阈值默认值）
   · models.Detection / FireEvent / ok_detection / now_epoch  -> 内联
   · import detect as detect_mod  -> 直调同名类
```

接进 02 的实时监控循环（与作弊识别并列）：`gui._cam_fire_update()`，
火警经 `linkage_bridge.report_fire()` 上报 03。

### 2.2 融入时发现并修掉 13 的一个**致命缺陷**（重点）

> **`detect.py` 的 `analyze()` 构造 `Detection` 时从来没给 `level` 赋值**，
> 而 `FireDetector` 的确认闸门是按 `det.level is not None` 计数的
> ⇒ **连击永远为 0 → 事件永不创建 → `on_alarm` 永不回调**。
>
> 也就是说：**13 能算出 0.78~1.0 的高分，却永远不会报警。**

这解释了为什么它的 `integration_api.py` 从来没被任何模块调用过 —— 接上也报不出警。
它的 **51 项自检 + 40 项单测都没覆盖这条路径**，所以长期没暴露。

另外修了两处：`ok_detection()` 传参语义错位（`'str' object has no attribute 'has_fire'`）、
缺少事件风暴防护（同一场火重复报）。

融入后实测（`02\_冒烟_火检.py`，**17/17**）：

```
空白/纯灰画面   -> 不报警（score 0.000）
跳动橙红火焰块  -> level=alarm score=0.782（连续 4 帧后触发一次）
画面恢复        -> 判为已解除
持续火焰 20 帧  -> 只报 1 次（事件风暴防护生效）
```

### 2.3 智能终端"发布命令"（01/02 能接收并回复）——全新能力

```
03 📡 命令台  ──POST /api/command──────────►  03 落库（commands 表）
                                                     ▲
01/02 command_runner.py --loop 15 ──GET /api/command?target=<本机>──┘
                                  执行（白名单）
              ──POST /api/command_result──►  03 落回执 + 写审计链（下发命令/命令回执）
```

**两条链路都实测通过**：业务链路 `_联调_发布命令.py` **21/21**；真实 HTTP `_联调_发布命令HTTP.py` **17/17**。

**命令白名单（两侧各存一份，必须一致）**

| 命令 | 作用 |
| --- | --- |
| `ping` | 主机名/平台/Python 版本/模块目录是否就绪 |
| `status` | 回报该模块 `integration_api.py --op status` 完整结果 |
| `logs_tail` | 回报本模块最新日志末尾 ≤200 行 |
| `selftest` | 跑一次该模块自检并回报退出码与末尾输出 |
| `rebuild_index` | 重建人脸特征索引（仅 01） |

**安全设计**

1. **两侧白名单**：03 的 `/api/command` 拒一次，设备端 `SUPPORTED` 再拒一次
   （用 `rm -rf /`、`format_c_drive` 验证都被拒）。
2. **没有任意代码执行通道**：无 `exec`/`shell` 类命令，每条都映射到既有的 `integration_api` op 或读日志。
3. **鉴权沿用既有令牌** `X-Exam-Token`；未配令牌时**跨设备来源直接拒**（fail-closed），只有回环免令牌。
4. **全程留痕**：下发与回执都进本机哈希链；命令台可清台账但**审计链不动**。
5. **按目标隔离**：每个设备只拉得到 `target` 等于自己标识的命令。

> 如实说明：拉取是**轮询**（默认 15 秒），不是服务端推送；设备标识靠 `EXAM_DEVICE_ID`
> 或计算机名，现场需保证全网唯一，否则会抢命令。

### 2.4 13 目录的去向 README

`13_AI火场识别与自动报警\README.md` 已重写为**去向说明**（代码去向表、接口、三个缺陷的修复记录、
算法与两条安全设计原样保留的说明、如何恢复独立运行的注意事项、以及"独立版仍带缺陷"的警告）。

## 3. 需求③：03 当"账号管理中心"+ 权限模型优化

三套账号体系原本互不相通：

| 模块 | 账号存哪 | 角色 |
| --- | --- | --- |
| 03 | `terminal.db` 的 `kv['accounts']` | owner/admin/patrol/… |
| 01 | `01/data/exam.db` 的 `users` 表 | owner/admin/teacher |
| 02 | `02/data/camera.db` 的 `kv['web.accounts']` | owner/admin |

**新增**

1. **01/02 各加 4 个 op**：`account_list / account_create / account_reset / account_delete`，
   都带 `by_role` 参数做**越级防护**（只能管严格低于自己的角色）。
2. **03 新增「跨机账号管理」窗口**：选目标模块 → 远程查看/新建/重置口令/删除。

**四道闸（缺一不可）**

1. 03 侧 `require("manage")` —— **仅所有者**；
2. 03 侧每次写操作先写本机审计链；
3. 对端 01/02 再判一次越级（并保留"至少一名管理员""不能删所有者"等既有约束）；
4. **口令只在内存里传给对端子进程，03 不落库、不写日志。**

**权限模型优化**：新增 `maintain` 动作 ——
**管理员（admin）可做数据维护**，但**硬删（hard）仍限所有者**（`HARD_PURGE_ROLES`）。
改造前 admin 连清空页签都看不到。

实测：能列出 01 的 `['owner','teacher1','admin']`、02 的 `['owner','teacher1']`；
以 teacher 身份删 01 的 owner → `权限不足：教师不能删除「所有者」账户`；
以 admin 身份删 02 的 owner → `权限不足：不能删除所有者账户`。

## 8. 如实说明（边界与未做）

1. **发布命令是轮询，不是推送**（默认 15 秒）；设备标识需现场保证唯一。
2. **01/11 没有 `integration_api.py`**，所以驾驶舱里它们显示"不可用"——这是如实呈现，不是缺陷。
   如需纳入，给它们各加一个 `status` op 即可（02/05/06/08/09/10 已有）。
3. **局域网传输是 HTTP 明文 + 令牌**，只适用于可信考场内网；跨不可信网络需反向代理 + HTTPS。
   这条是既有设计，本次未改。
4. **13 的原始文件未删除**（README 里说明了如何恢复独立运行）。
   需求里提到"删除内部冗余内容"，但删文件不可逆且会让独立版失效，因此采取了
   "融入 + README 说明去向 + 保留可恢复"的方式；若确认要物理删除，可另行执行。
5. **UI 驾驶舱风格目前落在 03**（主终端）。02/13 的主题化只做了色板层面的统一，
   完整套用需要改它们的界面代码，未在本轮完成。
6. 13 的 `ui_popup.py` / `tray.py` / `ui_main.py` **未搬迁**（03 终端与 02 界面已承担这些职责）。
