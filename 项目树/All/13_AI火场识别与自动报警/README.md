## 五、融入时修掉的三个真实缺陷（原独立版存在，务必知悉）

1. **`analyze()` 不给 `Detection.level` 赋值** —— 而 `FireDetector` 的确认闸门按
   `det.level is not None` 计数 ⇒ **连击永远为 0、事件永不创建、`on_alarm` 永不回调**。
   也就是说：**原版能算出 0.78~1.0 的高分，却永远不会报警**（`自检.py` 51 项与
   40 项单测都没覆盖这条路径，所以长期没暴露）。这也是它的集成接口从未被用起来的原因。
   → 已在 `fire_detect.py` 按阈值补上 `alarm`/`warning`/`None`。
2. **`models.ok_detection(...)` 传参语义错位**：原调用把"后端名"当第一个位置参传入，
   内联后签名变化会抛 `'str' object has no attribute 'has_fire'`。→ 已改为显式 `backend=`。
3. **无事件风暴防护**：同一场火反复触发。→ `FireWatch` 增加事件 ID 去重 +
   `event_cooldown_sec`（默认 20s）冷却。

算法与两条安全设计**原样保留**：单帧永不算数（连续 4 帧）、静态火色封顶（红布/红衣/红灯不报火警）。

融入后实测（合成画面，`02.../_冒烟_火检.py`，**17/17 通过**）：

```

```

## 三、检测原理（多信号融合，可解释、可标定）

默认后端**不是**深度学习模型，而是五个信号加权融合 —— 选它的理由是：
公开的火焰检测权重没法随代码交付（体积/授权/版本都不确定），
而"能解释、能现场标定、零额外依赖"对一台值班设备更要紧。
如果 `models\` 下放了 `fire*.onnx`，会自动切到 ONNX 后端（见第六节）。

| 信号 | 判据 | 为什么需要 |
| --- | --- | --- |
| **火色** | HSV 红(0~10/160~179)橙黄(10~35) + 高饱和 + 高亮度 | 火的基本外观 |
| **去肤色** | YCbCr 肤色掩膜外扩后扣除 | 人脸/手臂在 HSV 里也偏红黄，不排掉就会"人脸一动就报警" |
| **闪烁** | 区域平均亮度与面积的帧间抖动 | 火苗在抖；静止红布/红灯不抖 |
| **增长** | 区域面积随时间上升（最小二乘斜率） | 火在蔓延；灯光恒定、红布静止 |
| **烟雾** | 灰白 + 低饱和 + 极低边缘密度，且**比平静基线明显上升** | 早期征兆；只有烟时最高只判「疑似」，不单独定火警 |

### 两条关键的安全设计

1. **单帧永不算数**：必须连续 `confirm_frames`（默认 4）帧命中才报警。
   闪光灯、车灯扫过、红衣服飘过都只是"单帧高分"，进不了报警。
2. **没有时序证据的静态火色会被封顶**：
   一块静止的红布颜色与火几乎不可分，所以当区域**既无闪烁、又无增长、
   亮度饱和度也不突出**时，分数被压到疑似线以下（`warning_threshold × 0.8`）。
   真火必然有闪烁或增长，不会被这条挡掉。
   *（这条是实测踩出来的：早期版本上限正好卡在疑似线 0.400，
   静止红布照样把确认闸门喂满，进而误报。）*

### 现场标定

阈值全部可在界面「检测参数」里拖滑杆调，也可直接编辑 `data\settings.json`：

| 参数 | 默认 | 怎么调 |
| --- | --- | --- |
| `alarm_threshold` | 0.62 | 误报多就调高；漏报就调低 |
| `warning_threshold` | 0.40 | 「疑似」的门槛（只提示不响铃） |
| `confirm_frames` | 4 | 越大越稳、越小越灵敏 |
| `detect_interval_ms` | 200 | 越小越灵敏、越吃 CPU |
| `min_fire_px` / `min_fire_ratio` | 220 / 0.0012 | 小亮点算不算火（防远处一个红点就报） |
| `hsv_s_min` / `hsv_v_min` | 90 / 170 | 火色"够不够艳、够不够亮" |
| `skin_dilate_px` | 9 | 肤色排除的外扩范围 |
| `popup_on_warning` | false | 「疑似」是否也弹窗 |

> **如实说明**：合成画面上的判别力（真火报警、静止红布/肤色不报警）已由自检覆盖，
> 但**真实现场的阈值必须按现场灯光与机位标定**。这不是"调好了就一劳永逸"的模型。

## 四、报警时会发生什么

```
检测器确认（连续 N 帧达标）
   ├─ 事件落库（SQLite：fire.db）              ← 值班记录
   ├─ 证据线程写盘（不阻塞检测/界面）
   │     events\<事件号>\snapshot.jpg   抓拍原图
   │     events\<事件号>\marked.jpg     标注图（画了火色框+判定依据）
   │     events\<事件号>\clip.avi       告警前缓存段 + 后录 N 秒
   ├─ 审计日志追加（谁在什么时候确认/误报）
   └─ 火警弹窗
         · 自动置顶 + 抢焦点 + 闪任务栏（纯 tkinter 抢焦点不保证成功，闪任务栏兜底）
         · 响铃（60 秒无人处理自动静音，窗口留着）
         · 弹窗内嵌实时画面（带检测框），不是一张静态图
         · 值班动作：确认到场（留痕）/ 误报（留痕，供后续调参）/ 打开证据目录
         · 多次报警**追加到同一窗**，不叠一堆窗（叠窗反而看不清）
         · 火灭了只把标题改成"已解除"，**不自动关窗**（要人看过）
```

关于录像的**如实说明**：事件触发时手上只有"当前帧"，真正的"告警前 N 秒"
需要一直录才有。本实现把内存里缓存的最近若干帧先写进视频开头（近似前 N 秒），
再继续写 `post_seconds` 秒实况 —— 好处是平时一张帧都不落盘，不占磁盘。

## 八、已知边界（不谎报）

1. **检测器是传统视觉，不是深度学习模型**。五个信号都可解释、可标定，
   但真实现场的灵敏度必须标定；默认阈值是按合成画面调的起点，不是终点。
2. **本机没有可交付的火焰模型权重**。需要更高精度请自带 ONNX 模型（第六节），
   或把 `data\events\` 里的误报/漏报样本用于迭代。
3. **托盘在无桌面会话（服务/计划任务）里不可用**属正常现象。程序会**优雅降级**：
   退化为普通最小化，报警与弹窗逻辑完全不受影响。
4. 纯 tkinter **无法 100% 保证抢到前台焦点**（Windows 的系统限制），
   因此额外做了闪任务栏与响铃；极端情况下窗口可能不在最前，但任务栏一定会闪。
5. 录像的"告警前 N 秒"是**内存缓存近似**，不是一直落盘的完整前段（见第四节）。
6. 本模块是**值班提示设备**，不替代消防报警系统与人工处置：
   AI 只负责"尽早发现并把人叫过来"，处置权与责任仍在值班人员。
