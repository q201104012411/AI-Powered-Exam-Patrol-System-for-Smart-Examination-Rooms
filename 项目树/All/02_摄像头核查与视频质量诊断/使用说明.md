# 使用说明 · 摄像头核查与视频质量诊断

> 对应《[摄像头核查与视频质量诊断.md](摄像头核查与视频质量诊断.md)》。
> 本目录是**核查软件的真实现**（可运行、有测试）；真实摄像头/录像/音频对接与现场验收见文末。

## 一、怎么启动

| 想做什么 | 双击 |
| --- | --- |
| 打开核查界面（桌面） | **启动核查界面.bat**（先出登录页） |
| 打开核查网页版（浏览器） | **启动核查网页版.bat**（http://127.0.0.1:5010/） |
| 停止网页服务 | **停止核查网页版.bat** |
| 隐藏 / 显示启动器的黑窗口 | **切换命令行窗口.bat**（不用登录也能切） |
| 一键体检（单元测试 + 自检） | **运行自检与测试.bat** |

> 界面截图（登录页、所有者/管理员主界面、账户管理、审计链）在 `文档\界面截图\`，
> 可用来核对"按钮是不是真的按角色禁用了"。

### 默认账户（桌面端与网页版**同一份**，改一边另一边立刻生效）

| 用户名 | 默认口令 | 角色 | 能做什么 |
| --- | --- | --- | --- |
| `owner` | `owner` | 所有者 | 全部功能 + 删机位 + 终端账户管理 + 看审计链 + 隐藏 cmd 开关 |
| `teacher1` | `teacher1` | 管理员 | 台账登记、采基准图、三级巡检、工单派单/整改/复核、看指标与报告 |

> 口令只存 PBKDF2 加盐哈希（`pbkdf2$salt$dk`），界面不回显明文。
> **登录后建议尽快在「🔑 修改口令」里改掉默认口令。**

### 隐藏命令行窗口（不显示黑窗口）

- 所有者登录后，主界面右上角勾选 **「隐藏命令行窗口（下次启动生效）」** → 写入标记文件
  `data\hide_cmd.on`；取消勾选就删掉标记（改回显示黑窗口，便于看报错）。
- 管理员看不到这个开关（勾选框是灰的，属所有者专属）。
- 启动器逻辑：**检测到 `data\hide_cmd.on` 就用 `pythonw.exe` 启动（零黑窗口、立即返回）**，
  没标记就正常显示控制台。桌面端与网页端两个启动器都支持。
- 没登录/账户进不去时：双击 **切换命令行窗口.bat** 即可切换（每双击一次切换一次）。
- 数据目录被 `EXAM_CAMERA_HOME` 或 `camera_home.txt` 改到别处时，标记文件与启动器
  都会认那个新目录（三处都会查），不会"勾了没效果"。

### 账户管理（仅所有者）

- 桌面端：主界面右上角 **「👥 终端账户」**；网页端：**「👥 终端账户」页签**。
- 可以：列出账户（不显示明文口令）、新建账户、重置口令、删除账户。
- 规则（两端一致，方法层强校验，不是只藏按钮）：
  - 只能新建**低于自己等级**的账户 —— 所有者只能建管理员，**所有者账户不能被新建**；
  - 不能重置/删除所有者账户；不能删除当前登录账户；
  - 至少保留一个可用账户。
  - 管理员（teacher1）**完全不能**进账户管理，也不能删机位、看审计链、切隐藏 cmd。

网页版与桌面版能力一致：台账、基准图采集、三级巡检、缺陷与指标、工单闭环、报告导出；
另外网页版多一个 **「现场抽查」**——直接上传一张现场画面做诊断（现场没接摄像头时可用）。

命令行：

```bat
python gui.py                              :: 桌面界面（会先要求登录）
python 网页核查面板\server\app.py           :: 网页后端（端口 5010）
python -m unittest discover -s tests -t .  :: 233 项单元测试
python main.py                             :: 108 项自检（临时数据目录，不污染真实数据）
python main.py --real                      :: 用真实 data 目录自检
```

> 注意：网页端的**巡检**仍按机位的取流地址去抓帧；机位没填地址就会如实判"取流失败/离线"。
> 想在没有摄像头的情况下看诊断效果，用「现场抽查」上传画面，或用「采基准图」上传现场照片。

## 二、界面怎么用

> 桌面端界面上登录后，右上角显示**当前账号与角色**，并有「🔄 切换账号」（回登录页、清空输入）
> 与「退出」。受权限限制的按钮对管理员是**灰的并标注"（仅所有者）"**，就算绕过界面也拦得住。

### 1. 设备台账
- 「＋ 新增机位」登记：设备编码、考场、**安装位置**、取流地址、分辨率、**视场角/水平角/俯仰角**、场次
  （编码/考场/位置/视场角是台账必填项，缺了巡检时会报"台账不符"）
- 勾「配拾音器」则这台机位会参与音频链路核查
- 选中一行 →「📷 采集基准图」：**部署完成后必须逐机位采集基准图**，
  没有基准图就没法做遮挡与视角偏移核查（列表里基准图列显示"缺"，行是黄色底）
- 选中一行 →「🗑 删除机位」（**仅所有者**）：确认后删除该机位及其实基准图登记，
  已产生的核查记录与工单保留，删除动作进审计链
- 心跳列会实时显示该机位心跳状态

### 2. 巡检核查
- 三个按钮对应**三级巡检**：日常（30 分钟一轮）/ 考前专项（考前 7 天）/ 考前一小时自检（开考前 30 分钟）
- 跑完会在下方列出每次核查记录：**红色行=fail 级缺陷**，**黄色行=warn 级**
- 选中一行，底部显示该次核查的**全部实测指标**（清晰度、均亮、对比度、偏色、条纹、噪声、块效应、平移像素、角度、纹理丢失率、时钟偏差…）
- 巡检发现异常会**自动创建整改工单**

### 3. 整改工单
- 按「发现 → 派单 → 整改 → 复核」操作：
  1. 选工单 →「派单」→ 填整改责任人
  2. 整改完 →「提交整改」→ **必须选择整改后截图**（没图不给提交）
  3. 复核 →「复核通过」归档，或「复核打回」退回继续整改
- 顶部显示工单总数/已闭环/未闭环

### 4. 报告与指标
- 「生成并导出报告」：生成含**五项关键指标、缺陷汇总、整改闭环、逐考场逐机位明细、验收证据清单**的完整报告，导出到 `data\reports\`
- 未达标的指标会标 **未达标/样本不足** —— 统计为 0 不会显示成达标

## 三、数据放在哪

| 路径 | 内容 |
| --- | --- |
| `data\camera.db` | 台账、核查记录、工单、基准图登记、审计链、**账户（kv 键 web.accounts）** |

换位置：设环境变量 `EXAM_CAMERA_HOME`，或在本目录写 `camera_home.txt`。

所以两边账户、口令永远一致；换数据目录等于换了一整套账户。

## 四、判定逻辑速查

| 现象 | 判为 | 依据 |
| --- | --- | --- |
| 画面糊 | BLUR | 清晰度（拉普拉斯方差）低于下限 |
| 一片黑/一片白 | UNDEREXPOSED / OVEREXPOSED | 平均亮度、暗/亮像素占比 |
| 灰蒙蒙没层次 | LOW_CONTRAST | 亮度标准差 |
| 整体发蓝/发红 | COLOR_CAST | 通道均值偏离（灰度世界假设） |
| 横竖纹 | STRIPES | 行/列投影的周期分量占比 |
| 雪花点 | SNOW | 中值滤波残差标准差 |
| 方块 | MOSAIC | 块效应（**原生分辨率**上，行/列同相位都强） |
| 画面不动 | FROZEN | 连续多帧帧间差≈0 |
| 被挡/被喷 | OCCLUDED | **基准有纹理处丢失纹理** + 边缘密度下降 |
| 镜头被转 | VIEW_OFFSET | 相位相关求平移 → 按视场角换算角度 |
| 有盲区 | COVERAGE_LOW | 有效纹理覆盖率过低 |
| 录像断档 | REC_GAP / REC_MISSING | 段索引缺口 / 无段可回放 |
| 时间不对 | TIME_DRIFT | 与标准时间偏差 >1 秒 |
| 没声音/一直吵 | AUDIO_SILENT / AUDIO_NOISE | RMS + 过零率 |
| 台账没填全 | LEDGER_MISMATCH | 编码/考场/位置/视场角缺失 |

**多算法融合**（降误判）：过暗过曝时不再叠加模糊/低对比/块效应/遮挡；报了遮挡就不再报块效应；
报了条纹就不再报雪花；画面几乎纯色时不判块效应与遮挡。

**AI 行为判据（2026-10 实测修正）**：越界与偏转两条判据原先都不成立，已改：

| 行为 | 旧判据（问题） | 新判据 |
| --- | --- | --- |
| 越界 | 只看"框底越过警戒线"——人框本就延伸到画面底部，**画面里有人就必然报越界**，把警戒线从 92% 挪到 98% 也没用 | 框底越线 **且** 头顶下移到画面 45% 以下（真走到镜头前/离开座位） |
| 大幅度偏转 | 固定宽高比阈值 0.85——实测**正常坐姿宽高比就有 1.386**，坐着不动必然误报 | 宽高比 > **本轨迹历史中位数 ×1.15**，或 >1.6（明确侧身形态）；自适应站/坐与远/近 |
| 前倾/趴桌 | 固定 0.68（同样不适配坐姿） | 宽高比 > 本轨迹历史中位数 ×1.08，且框高在收缩 |

实测对照（连续 4 帧确认）：坐姿不变 -> 不再报偏转；明显侧转 +30% -> 仍能报出；
远距离侧转（基线 0.55）-> 旧逻辑漏报，新逻辑能报出。
（11 摄像头 AI 识别目录已删除，相关逐人检测代码已并入 02 的 `person_detect.py`。）

## 五、AI 检测模型（YOLO11n，2026-10-14 已随包分发）

### 检测链（固定优先级，自动选择）

程序启动时按**固定顺序**自动选，**界面与配置都无法指定后端族**：

| 优先级 | 后端 | 能拿到什么 | 触发条件 | 本目录现状 |
| --- | --- | --- | --- | --- |
| 1 | **YOLO11n ONNX**（主力） | 人框 | `models\yolo11n.onnx` 存在且装了 `onnxruntime` | **已就绪**（模型随包携带） |
| 2 | **MobileNet-SSD**（兼容保留） | 人框 | 本目录存在 `MobileNetSSD_deploy.prototxt` + `.caffemodel` | 缺模型，未参与 |
| 3 | **HOG+SVM**（内置兜底） | 人框 | 以上都不可用 | 可用（兜底） |

- YOLO11n **输入固定 640×640 letterbox**，**只解码 COCO 的 person 类**（输出 `[1,84,8400]`）；
  它**不做姿态点、不做手机类识别**。
- **YOLO 可用时，某帧零检出仍会再跑一次 HOG 兜底并把结果合并**（新版行为）。
- 依赖 `onnxruntime`；**缺失或没有模型时静默回落 HOG**，不报错、不崩。
- 同一个人被检成"头/上半身 + 整体"时会**自动去重**（只留整体框）；Haar 人头与背景差分
  两个辅助源改成**只在主链零检出时兜底**（旧版"人数 < 8 就叠加"会让单人特写画面里
  一个人被画出一堆框）。

### 模型放哪里、怎么换

- 默认读 `models\yolo11n.onnx`（本目录已随包携带，**无需自己下载**）；
- 想换别的 onnx：设环境变量 `EXAM_YOLO_MODEL` 指向那个文件；
- 想强制禁用 YOLO（做对比/排查）：`EXAM_YOLO_DISABLE=1`；
- 苹果机器想优先 CoreML：`EXAM_YOLO_EP=coreml`（失败自动回退 CPU）；
- 两个现成工具（都在本目录）：
  - `python 工具_YOLO模型导出.py` —— 用 ultralytics 从官方 `yolo11n.pt` 导出 onnx
    （一次性依赖 `pip install ultralytics onnxslim`；改脚本里的 `MODEL_NAME` 可换 yolo11s 等）；
  - `python 下载模型.py` —— 从 ultralytics **官方 release** 下载预导出 onnx 并校验 SHA256
    （内置 `yolo11n.onnx`（默认下载）与 `yolo11s.onnx` 两个**检测**模型，`--list` 可看，
    `--check` 只查本地已有文件）。
  - 注意：本目录随包的 `models\yolo11n.onnx` 是**本机用导出工具导出的**（simplify=True），
    哈希与官方 release **不同属正常**，能正常推理即可。

### 确认当前用的是哪条检测链

```bat
python 工具_模型对比.py --selftest
```

会打印本机 OpenCV 版本与一行**检测链**说明。本机（2026-10-14）实测输出为：

`OpenCV 4.14.0` / `检测链：YOLO11n 就绪(yolo11n.onnx)；MobileNet-SSD 缺模型；HOG+SVM 兜底可用`

`--selftest` 打印的是"**当前检测链会跑什么**"，不再是旧版的"推理后端探测"结果。

### 对比实验（写报告/答辩用）

```bat
python 工具_模型对比.py --selftest                     :: 只看检测链可用性
python 工具_模型对比.py --video data\captures\考场1.mp4 :: 用真实录像对比
python 工具_模型对比.py --images data\captures          :: 用现场抓帧对比
python 工具_模型对比.py --images data\captures --gt data\gt  :: 有标注时出精确率/召回率/F1
```

对比的是 **YOLO11n-ONNX 行 vs HOG+SVM 行**（MobileNet-SSD 行在缺模型时如实标"未参与"），
输出速度（中位/P95）、人数波动、轨迹连续性，并在 `data\reports\` 留一份 Markdown 报告。

常用参数：

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `--model` | `models\yolo11n.onnx` | YOLO onnx 路径（也可用 `EXAM_YOLO_MODEL` 覆盖） |
| `--conf` | `0.25` | YOLO 置信度阈值 |
| `--input-dim` | `640` | 对比用长边（**界面三档统一 640**，再放大也不会更准） |

**注意**：缺模型的后端会明确标为"未参与"，不会拿 HOG 的数字冒充 YOLO/SSD 的结果。

### 关于 GPU

- **pip 安装的 `opencv-python` 没有编译 CUDA**，`cv2.cuda.getCudaEnabledDeviceCount()` 恒为 0，
  所以 `cv2.dnn` 走不了独显；OpenCL 在笔记本上默认落到**核显**，实测并不提速。
- YOLO11n 走 `onnxruntime`：本机装的是 **CPU 版 onnxruntime**，实测就是 CPU 推理；
  苹果机器可用 `EXAM_YOLO_EP=coreml` 优先 CoreML（失败自动回退 CPU）。
- **GPU 路线本机未实测**：`onnxruntime-gpu` / DirectML 等能不能提速，本机没有可复现的数字，
  换机器后请先跑 `工具_模型对比.py` 看数据再下结论。
- HOG 兜底路径在 640 长边下的耗时约 **33 ms/次**（旧引擎/旧三档时期的实测，见下方「算法实测调优」），
  按界面标准模式 500ms 分析间隔算，单路约占 13% CPU。
  真正该换模型的原因是**密集考场识别准确率**，不是速度 —— **不要为了"上 GPU"而上 GPU**。

### 手机识别（**该能力已随 2026-10-14 模型层替换下线**）

> **以下均为旧引擎（含 cell phone 类的检测链）时期的实测记录，该能力已随 2026-10-14
> 模型层替换下线，数据保留作为项目的决策依据。**
> 现在的检测链**只解码 COCO 的 person 类，不做手机识别**：逐人信息里没有手机相关字段
> （现为 `pid / rect / action / bad / crosses / behaviors / density_level`），
> 界面上也没有手机计数、没有手机相关告警与红框。

旧引擎当时确实实现过手机（COCO `cell phone` 类）识别并与人体框关联，
但**实测未达到可用水平**（实测时间 2026-10，原始数据如下）：

- 拿**确知画面里有手机**的真实照片测，`cell phone` 类峰值置信度只有 **0.0001~0.0007**；
- 把手机区域裁切放大 4 倍后是 **0.005**；合成"清晰手机"画面是 **0.001**；
- 输入分辨率 640 / 960 / 1280 三档全部 ≈0，**与分辨率无关**。

也就是说该链路对"考场里学生手上的手机"基本无响应，**调阈值救不回来**
（旧链路手机阈值是 0.60，比人的 0.30 更严，就是为了压住无关画面里约 0.50 的候选）。

**要做手机识别，只有三条路：**
1. 用考场实拍**微调专用模型**（最可行）；
2. 换更大的模型（**存疑、未实测**）；
3. **接入 `06_智能安检与手机作弊器材检测` 模块**。

**结论（三条，逐条可核对）**

1. **当前不具备手机识别能力**：现检测链只解码 COCO 的 person 类，不输出手机类结果；
   逐人字段里没有手机相关项，界面也没有手机计数、手机告警与红框。这不是"配错了"，
   是**能力已下线**（2026-10-14 模型层替换）。
2. **调阈值救不回来**：旧链路对确知有手机的画面，峰值置信度只有 0.0001~0.0007；
   裁切放大 4 倍 0.005、合成清晰手机 0.001，640 / 960 / 1280 三档输入全都 ≈0；
   而旧链路手机阈值本就已经压到 0.60（人的 0.30、无关画面候选约 0.50）——
   在 0.0007 量级上再调阈值，只会把噪声变成误报。
3. **要这个能力走第 3 条**：接入 `06_智能安检与手机作弊器材检测`（判据引擎 + 保管柜闭环），
   而不是在 02 的视频链上继续加模型。第 1、2 条留作后续可选路线（第 1 条最可行，
   第 2 条**存疑、未实测**）。

> 本节所有数字都是**旧引擎时期的历史实测**，只用于说明"为什么下线"；
> 现行检测链不做手机识别，因此不存在"当前手机识别指标"，也不能用 `[待实测]` 表示——
> 该能力已从代码里移除。

### 密集考场（40 人）：必须用「密集」模式

一个 1080p 机位看 40 个考生时，后排只有几十像素高。"标准"模式把整帧压到 640 送模型，
后排必然漏检；**而且把分辨率调到 1280/1920 也没用** —— 单张推理照样会把整帧压回 640。

本版为此做了两件事：

1. **密集档 = 分析长边 1280**（AI 设置 → 检测模式选「密集」）；
2. **分块（切片）推理**：把画面切成与模型输入同尺寸（640）的块，每块按**原生像素**
   送模型，等效放大 2~3 倍，后排才看得见。`yolo_tiling=auto` 只在大画面启用；
   **有人贴脸（大目标）时自动不分块**，避免把一个人切成好几块。

实测（`python 工具_密集场景评测.py`，合成 40 人考场，人物外观取自真实抓拍）：

| 配置 | 召回 | 精确 | 单路分析耗时 |
| --- | --- | --- | --- |
| 640 单张（原默认） | 12.5% | 71% | 27 ms |
| 1280 单张 | 22.5% | 90% | 27 ms |
| **1280 + 分块（密集档默认）** | **62.5%** | **89%** | 约 200 ms |

- 人多时（> 12 人）逐人标签自动简化：只给异常/越界/手机框写文字，画面不会被文字糊死；
- 想更准：先用 `python 工具_密集场景评测.py --tile-size 480` 看数字，再改
  `data\ai_settings.json` 里的 `yolo_tile_size`（更准更慢，约 2 倍耗时）；
- 换更大模型（`yolo11s`）是下一步提升召回的手段：`工具_YOLO模型导出.py` 改 `MODEL_NAME`，
  或 `下载模型.py` 拉 `yolo11s.onnx`（本机未实测）；
- **如实说明**：上表是合成场景的横向对比，**不代表真实考场准确率**；真实指标必须用现场样本。

### 算法实测调优

> 下表中标了「旧引擎实测」的行是**旧引擎（HOG 为主力）时期的实测数据**，保留作对照；
> 现在三档长边已**统一 640**（原因见第 2 行），旧数据里的 416 / 576 / 320 长边已不再使用。

| 项目 | 改前 | 改后 | 依据 |
| --- | --- | --- | --- |
| HOG 密集网格 dense（旧引擎实测） | 小图上也强制开 | **按送检尺寸自适应**（≥1000px 才开） | 416 长边：45.9ms/4 人 → 7.3ms/5 人；640：134ms/4 人 → 33.2ms/5 人 |
| AI 分析长边 | 旧三档 416 / 576 / 320（其间曾改为 640 / 768 / 416） | **三档统一 640**（standard / dense / energy） | YOLO11n 输入固定 640×640，长边再大也不会更准；旧实测：416 下"坐着的人"仅约 70px 高，而 HOG 窗口要 128px，必然漏检 |
| 生产路径耗时（旧引擎实测） | 416 下 54.9 ms/次 | **16.1 ms/次（提速 3.4×）** | 9 路单核占用 99% → 29% |

实测检出人数（旧 HOG 引擎，合成 24 人教室，仅说明相对趋势）：416 → 4~5 人，640 → 6 人，原生 1080p → 7 人。
**HOG 本质上就是检不全密集考场**，所以现在主力已换成随包分发的 YOLO11n，HOG 只做兜底。

三档（标准 / 密集 / 节能）现在**长边统一 640**，差别只在分析频率与跳帧
（标准 500ms / 密集 900ms / 节能 1600ms 一次，节能档另有跳帧）；
算力紧张时仍可切**节能**，但**不会再降分辨率**。

### 多模态大模型（VLM）检测（本版新增，可选但推荐）

本版把检测源换成了**能看图的多模态大模型**：由模型直接判读"谁在干什么、有没有手机小抄"，
YOLO11n 保留为兜底。**不开启多模态时，界面与行为与上一版完全一致。**

| 后端 | 需要填什么 | 适合 |
| --- | --- | --- |
| 关闭（off） | — | 只想用 YOLO11n（等于上一版） |
| 本机 Ollama | 模型名（如 `qwen2.5vl:3b`） | 数据不出本机、离线可用 |
| OpenAI 兼容 API | 模型名 + 接口地址 + API Key | 追求准确率，接受联网与费用 |

> ⚠ **Ollama 必须用"能看图"的模型**。本机目前只有 `Qwen3-4B`（纯文本），
> 它**不能看图**，多模态会一直如实回落 YOLO11n。先拉一个视觉模型：
> `python 工具_多模态检测.py --pull`（默认 qwen2.5vl:3b，约 3~4GB）。

**怎么开**：界面「实时监控 → AI 设置 → 多模态大模型」里选后端、填模型名，
点「测试连接」看是否通过，再点「保存」（下次分析会重建检测器）。
命令行等价做法：`python 工具_多模态检测.py --provider ollama --model qwen2.5vl:3b --write-settings`。

**怎么验证**：`python 工具_多模态检测.py --check` 看配置与连通性；
`python 工具_多模态检测.py --image <一张考场图>` 会打印模型的 JSON 并把框画出来存到
`data\reports\`；双击 `多模态检测.bat` 是同一套功能的菜单。

**参数**（`data\ai_settings.json`，前 4 项界面里也能改）：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `vlm_provider` | `off` | `off` / `ollama` / `api` |
| `vlm_model` | 空 | `qwen2.5vl:3b`（ollama）/ `qwen-vl-max`（api）等 |
| `vlm_base_url` | 空 | 留空=默认（ollama→127.0.0.1:11434） |
| `vlm_api_key` | 空 | 只有 api 需要 |
| `vlm_interval` | 3.0 | **每路每 N 秒最多一次**多模态调用（多模态慢，别小于 2 秒） |
| `vlm_max_dim` | 896 | 送模型的图片长边（调小更快） |
| `vlm_timeout` | 60 | 单次调用超时（秒） |

**结果怎么用**：模型返回 `persons[{box,action,confidence}]`、
`objects[{box,label,confidence}]`（手机/小抄/耳机/智能手表/平板/书本）、`summary`。
人框进原有跟踪链路（编号、三色框、越界判定都不变）；行为词经归一后进行为标签与告警；
可疑物品画橙色框（**手机为红色**），落在人框里的物品会记到该人身上并并入「使用手机」行为。

**如实说明**：多模态比 YOLO 慢得多（本机 CPU 跑 3B 级通常每次 **2~10 秒**），所以是
**按间隔抽样判读**、两次之间沿用上一次结果；一旦超时/报错/结果过期，本帧自动回落 YOLO11n。
状态栏会写清谁在出框：`AI：N 路 … ｜ 多模态 <模型>：结果新鲜 / 回落 YOLO11n`，
并写 `data\ai_backend.txt`。模型没返回合法 JSON 或框不合法时按本次失败处理，**绝不编造人数**。

## 七、注意事项

1. **必须先采基准图**：遮挡与视角偏移完全依赖基准图；没基准时界面会提示，指标里也会标注
   `baseline_missing`，不会假装做过视野比对。
2. **块效应在原生分辨率上算**：这是刻意的——缩放到统一工作宽度会把块边界插值抹平，
   导致马赛克与正常画面无法区分。
3. **取流有超时保护**：错误的 RTSP 地址不会把巡检卡死（默认 6 秒超时）。
4. **整改必须留前后截图**，否则提交不了——这是验收证据要求。
5. **复核不通过会打回**，不会"点一下就算闭环"。
6. **关键指标不能造假**：样本为 0 时统一显示"未达标/样本不足"。
7. **审计链**：台账登记、核查、工单各步、报告导出、**登录成功/失败、账户增删改、切换隐藏 cmd**
   都进 `sha256(prev+规范化JSON)` 哈希链；审计链只有所有者能看。
8. **默认口令请尽快改**：`owner / owner`、`teacher1 / teacher1` 是预置口令，
   正式使用前应在「🔑 修改口令」里改掉。
