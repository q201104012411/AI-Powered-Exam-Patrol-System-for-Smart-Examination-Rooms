# 00 集成联动 · 多套系统互相调用

把各套系统串成一条链：**谁（01）+ 画面可不可信（02）+ 有没有作弊行为模式（作弊识别）+ 怎么处置（03）+ 门口拦不拦得住（06）**。

| 系统 | 回答的问题 | 提供的能力 |
| --- | --- | --- |
| **01 人脸识别与身份核对** | 这个人**是不是本人** | 1:1 / 1:N 人脸核验、证件信息带出、哈希链审计 |
| **02 摄像头核查与视频质量诊断** | 这个机位**画面可不可信** | 无参考画质诊断、基准图比对（遮挡/视角偏移）、工单闭环、**告警可信度系数** |
| **作弊识别**（`作弊识别\` + `cheat_bridge.py`） | 这段动作序列**像不像在获取/传递答案** | 加权风险分数 + 滑动窗口 + **持续超阈才告警**（单帧瞬时动作自动抑制）；摄像头路径下手部/物体信号**如实标注为不可得** |
| **03 智能终端操作** | 告警**怎么处置、怎么留痕** | 分级展示、红色强制确认、复核留痕、断网补传、考场时钟、终端权限 |
| **06 智能安检与手机作弊器材检测** | 手机/耳机**拦没拦住** | 安检门判据引擎、复检处置、手机集中保管、特殊考生人工通道、检出率证据 |

## 二、联动链（已实测跑通 39/39）

```
① 02 登记机位 + 采集基准图
        ↓
② 02 现场画面诊断
     正常画面 -> 无缺陷            -> 可信度 ×1.0
     模糊画面 -> BLUR(fail)        -> 可信度 ×0.5
        ↓
③ 02 -> 03 告警接入（带上该机位的可信度系数）
     可信度 0.5 的机位：红色预警【自动降级为橙色】+ 标注原因，防止画质误报堆积
     可信度 1.0 的机位：保持红色 + 强制确认
        ↓
④ 01 人脸核验（附机位画质上下文）
     可信度 < 0.8 -> 结论标注「该机位画质可信度 ×0.5，核验结论需人工复核」
        ↓
⑤ 03 复核结论回流留痕 + 审计链校验
     画质问题本身由 02 的整改工单闭环（发现→派单→整改→复核）
        ↓
⑥ 06 安检门判据引擎
     手机/无线耳机 -> PHONE_DETECTED（红）   金属/强磁/鞋底 -> SECURITY_ALARM（橙）
        ↓
     经本模块进 03 分级处置 -> 06 复检结论（放行/暂扣/转人工通道/误报）留痕
     查获器材自动存入手机保管柜（人-物-时闭环）
```

实测输出摘录：

```

PASS 模糊画面判为异常且识别为 BLUR   缺陷：['BLUR']

PASS 低可信度机位的红色预警被降级为橙色   level=orange 降级=True
PASS 画质正常机位的红色预警保持红色且需强制确认  level=red force_confirm=True
PASS 核验结论附带了机位画质可信度      ×0.5
PASS 画质不可信的机位会给出人工复核提示
PASS 复核结论已回流留痕
PASS 03 审计链完整
PASS 06 判出手机报警（双判据 -> 红）

PASS 复检结论在 06 留痕（查获暂扣并入柜）
联动自检通过：39/39 项全部符合预期
```

## 三、为什么用子进程 + JSON 而不是直接 import

各套系统**各自都有 `config.py` / `models.py` / `storage.py`**，
同进程 import 必然撞名（互相覆盖）。所以每套各留一个 `integration_api.py`：

```
01_人脸识别与身份核对\01_人脸识别与身份核对\integration_api.py   ops: verify / status /
                                                                     account_list /
                                                                     account_create /
                                                                     account_reset /
                                                                     account_delete
02_摄像头核查与视频质量诊断\integration_api.py                   ops: credibility / inspect /
                                                                     devices / save_device /
                                                                     baseline / status /
                                                                     account_list /
                                                                     account_create /
                                                                     account_reset /
                                                                     account_delete
03_智能终端操作\integration_api.py                               ops: ingest_alert /
                                                                     review_alert /
                                                                     list_alerts / status
06_智能安检与手机作弊器材检测\integration_api.py                 ops: ingest_pass / list_alarms /
                                                                     reinspect / report_alarm /
                                                                     add_locker / store_phone /
                                                                     take_phone / replay_test /
                                                                     metrics / report / status
```

> `account_*` 这组 op（2026-10-15 新增）供 **03 智能终端当"账号管理中心"** 远程管理
> 01/02 的登录账号。调用方需带 `by_role`（以什么角色发起），对端会做一次越级防护
> （只能管严格低于自己的角色），所以 01/02 的账号不会因为这条通道被越权改动。

统一调用形式（本模块 `linkage.Project.call` 就是这么调的）：

```bat
python integration_api.py --op credibility --args "{\"device_code\":\"CAM-A01-1\"}"
# 输出最后一行 JSON：{"ok":true,"factor":0.5,"reason":"该机位存在 画面模糊/失焦，可信度 ×0.5",...}
```

好处：命名空间互不干扰、可以单独调试、哪套崩了不影响其他两套。
换任何一套的实现（甚至换成 Java/Go 服务），只要能接这个 JSON 协议，联动层不用改。

## 五之二、作弊识别怎么进来的（2026-10-14）

链路里的位置：**02 画面可不可信 → 作弊识别（动作序列）→ 03 分级处置**。

```
③.5 作弊识别（时序引擎）-> 03 告警
     安静答题/伸懒腰（瞬时动作）  -> 不告警（时间维度抑制）
     持续偷看邻座 / 传递纸条 / 使用手机 -> 触发告警（红色）
        ↓
     经 00 送进 03 -> 同样带 02 的机位画质可信度：低可信度机位自动降级为橙色
```

实测（`python main.py` 里 `[4/7]` 一节）：引擎可用、安静不告警、伸懒腰被抑制、
持续偷看告警、使用手机告警、告警进 03、带可信度并按可信度降级 —— 共 7 项。

**如实说明**：摄像机路径下，引擎自己声明 **手部交互 / 违禁物体 / 表情 = 不可得**（没有骨骼点与物体模型），
结合层原样透出；物体类证据要**多模态大模型判读**才拿得到。角度是**估计值**，需按机位标定。


## 五之三、局域网联动：设备 A 的 01/02 记录上传到设备 B 的 03（2026-10-15）

**问题**：两台设备在同一局域网，一台跑 01/02，另一台跑 03 智能终端，
前者的操作记录能不能传到后者？——**能，而且已经跑通**（38 项端到端自检）。

| 层 | 文件 | 干什么 |
| --- | --- | --- |
| 接收端（设备 B，03） | `03_智能终端操作\lan_service.py` | HTTP 接入服务：`POST /api/records`（记录）、`POST /api/ingest_alert`（告警）、`GET /api/status|alerts|records`（只读）。默认只监听 127.0.0.1，跨设备必须令牌 |
| 传输（两端共用） | `00_集成联动\lan_upload.py` | 组批、队列、断网补传、幂等重发。**只依赖标准库**，01/02 直接 import |
| 发送端（设备 A，01） | `01_...\push_oplog.py` | 上报 `oplog`（界面操作日志）+ `verify`（核验记录哈希链，含链头与自校验结论） |
| 发送端（设备 A，02） | `02_...\push_oplog.py` | 上报 `audit`（审计留痕）+ `check`（机位核查结论）+ `order`（整改工单） |
| 编排层 | 本目录 `linkage.py` | `Linkage(terminal_url="http://<B的IP>:9113", terminal_token="...")` → p03 换成 `RemoteTerminal`，**上层编排一行不改** |
| 自检 | 本目录 `lan_selftest.py` | 真起 03 接入服务 + 真跑 01/02 客户端 + 断网补传 + 幂等 + 令牌鉴权（38 项） |

一键验证：双击 `局域网联动自检.bat`。设备上怎么用：

```bat
:: 设备 B（智能终端）：开局域网接收，记下令牌
双击 03_智能终端操作\启动局域网接入服务.bat     :: 监听地址填 0.0.0.0

:: 设备 A：填终端地址与令牌即可（会记住）
双击 01_人脸识别与身份核对\01_人脸识别与身份核对\上报到智能终端.bat
双击 02_摄像头核查与视频质量诊断\上报到智能终端.bat
:: 或常驻： python push_oplog.py --loop 120
```

**如实说明（跨设备部分的边界）**

1. 远端记录进 03 的 `remote_records` 表，**不与终端自己的哈希链合并** ——
   合并会让终端的 `verify_chain()` 立刻报"被篡改"。终端链上只写一条接入回执；
   对端声明过的链头存进 `remote_devices`，链头变化会留痕，但终端**验不了对端的完整链**
   （它只有增量记录），所以"链是否自洽"是对端自报的结论，不是终端的验证结论。
2. 传输是 HTTP 明文 + 令牌鉴权，只在**可信考场内网**用；跨不可信网络需反向代理 + HTTPS。
   接入服务开放"记录接入 / 告警接入 / 只读查询 / 发布命令"；**复核与远程擦除不经网络**。
   命令通道只接受固定白名单（见第五之四节），不是任意命令执行入口。
3. 设备 A 上的 01/02/06 仍是**本机子进程**调用（`Project`）；只有 03 可以走远端。
   一台设备内跑全部模块的用法完全不变（`Linkage()` 不传 `terminal_url` 即老行为）。
4. 01 的证件类字段（`id_card*`）在上报前被剔除，操作日志再脱敏一次；终端落库时逐字段加密。

## 五之四、智能终端"发布命令"：03 指挥 01/02 并收到回复（2026-10-15）

**问题**：前面几节都是 01/02 **单向**把数据推给 03。那 03 能不能**主动下发指令**，
01/02 收到后执行并**回复结果**？——**能，已跑通**（HTTP 端到端 17 项 + 业务链路 21 项）。

```
03 智能终端（指挥端）                    01 / 02 设备（被指挥端）
  📡 命令台下一条命令                      00_集成联动\command_runner.py --loop 15
        │                                        │
        │  POST /api/command                      │  GET /api/command?target=<本机标识>
        │  {target, kind, params}                 │  ← 拉到待执行命令
        └───────────────►  03 落库（commands 表）─┘
                                                 │  执行（**白名单**，见下）
                                                 │  POST /api/command_result
        ◄────────────────────────────────────────┘  {cmd_id, ok, result}
  03 落回执 + 写审计链（"下发命令" / "命令回执"），命令台显示结果
```

**命令白名单（两侧各存一份，必须一致 —— 这就是"没有任意命令执行通道"的保证）**

| 命令 | 做什么 | 备注 |
| --- | --- | --- |
| `ping` | 回报主机名/平台/Python 版本/模块目录是否就绪 | 不调业务接口，用于连通性排查 |
| `status` | 回报该模块 `integration_api.py --op status` 的完整结果 | 最常用 |
| `logs_tail` | 回报本模块 `data\logs` 下最新日志的末尾若干行（≤200 行） | 参数 `{"lines": 50}` |
| `selftest` | 跑一次该模块自检脚本，回报退出码与末尾 25 行 | 参数无 |
| `rebuild_index` | 重建人脸特征索引 | 仅 01 支持 |

**怎么用**

```bat
:: —— 设备 B（03 智能终端）：开局域网接收，记下令牌
双击 03_智能终端操作\启动局域网接入服务.bat      :: 监听地址填 0.0.0.0，记下令牌

:: —— 设备 A（01 或 02）：起命令执行器（把 bat 里的 MODULE 改成 01 或 02）
set EXAM_TERMINAL_URL=http://<B的IP>:9113
set EXAM_TERMINAL_TOKEN=<上面那个令牌>
双击 00_集成联动\启动命令执行器.bat

:: —— 回到 03 的界面：📡 命令台 页签 → 填目标设备标识 → 选命令 → 下发
```

也可以不开界面，直接用 HTTP：

```bat
curl -H "X-Exam-Token: <令牌>" -H "Content-Type: application/json" ^
     -d "{\"target\":\"PC-A-01\",\"kind\":\"status\"}" ^
     http://<B的IP>:9113/api/command
```

**安全设计（这一节是重点）**

1. **两侧白名单**：03 的 `/api/command` 拒绝白名单外的 `kind`；
   设备端执行器 `SUPPORTED` 也拒绝一次。**两边都过不去才是真拒绝**
   （联调里用 `rm -rf /`、`format_c_drive` 验证过都被拒）。
2. **不做任意代码执行**：没有 `exec` / `shell` 类命令，每个命令都映射到
   既有的 `integration_api.py` op 或读日志。
3. **鉴权沿用既有令牌**：跨设备一律校验 `X-Exam-Token`；
   未配置令牌时**跨设备来源直接拒**（fail-closed），只有回环地址免令牌。
4. **全程留痕**：03 每次下发与收到回执都写进本机哈希链审计
   （`下发命令` / `命令回执`），命令台还能清理台账但**审计链不动**。
5. **按目标隔离**：每个设备只拉得到 `target` 等于自己标识的命令（服务端精确比对）。

**如实说明**：拉取是**轮询**（默认 15 秒），不是服务端推送；设备标识靠
`EXAM_DEVICE_ID` 或计算机名约定，现场部署时请确保全网唯一，否则会出现抢命令的情况。

## 六、如实说明

1. 联动默认是**同一台机器上的进程间调用**（子进程 + JSON）；**多机部署**（跨设备）已由
   第五之三节的接入服务 + 上报客户端支持：01/02 的记录与告警能上传到局域网上的 03，
   `linkage.py` 也能把 p03 指向远端终端而编排逻辑不变。
2. 01 的核验在传"文件来源"时按严格模式返回 `LIVENESS_UNAVAILABLE`（防翻拍），
   这是**设计如此**；现场实时视频流走 01 自己的摄像头通道才有活体结论。
3. 02 的"可信度系数"依据该机位**最近一次**核查结果（fail ×0.5 / warn ×0.8 / 正常 ×1.0，下限 0.3）。
   所以联动自检里顺序很重要：先诊断、后发告警。
   安检门（06）不是摄像机机位，02 会回答"未知机位，不降权"，因此安检告警不会被降级。
4. 06 的报警**默认由 06 自己推给 03**（`06/linkage_bridge.py`，可在 06 界面逐条上报或开自动上报）；
   本模块的 `security_*` 接口是给脚本与联动自检用的入口。
