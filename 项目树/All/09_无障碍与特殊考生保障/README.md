> 所属：项目六 · 智能化装备与考生数据保护 ｜ 专题 09 ｜ 类型：自主补充
> 一句话：**别让智能化设备本身变成新的不公平** —— 给特殊考生留出"人工兜底"的替代路径，
> 并且把这条路径配置、演练、使用、整改的每一步都变成可查的证据。

本目录原来只有一份要求文档（[无障碍与特殊考生保障.md](无障碍与特殊考生保障.md)）。
现在它有了**可运行的实现**：通道台账与合规校验、特殊考生档案与保障措施、替代核验（人工兜底）、
因技术原因受阻事件、算法公平性分层测试、演练、关键指标与验收报告、以及和 00/01/02/03/06 的联动。

```

一键演示.bat      往 %TEMP%\acc09_demo 造演示数据并用它启动界面（不动真实数据）
```

> **启动方式说明**：默认走 `pythonw.exe` 无窗口启动，命令行窗口起完即退、不驻留；
> 想看到 Python 的报错就用 `启动.bat console`（或在命令行里跑 `python app.py`）。
> 无窗口启动若失败**不会静默**：异常会写进 `data\logs\app_console.log` 并弹窗提示日志位置。
>
> `无窗口启动.vbs` 保存为 **UTF-16 LE + BOM**，这是刻意的：WSH 按 ANSI 读取 `.vbs`，
> 若用 UTF-8（无 BOM）存中文，`。`+引号 这类字节组合会被当成一个双字节字符**吃掉引号**，
> 报"未结束的字符串常量"。改这个文件时请保持 UTF-16 LE + BOM（或全 ASCII）。

## 一、这个模块解决什么问题

智能化核验（人脸闸机、刷脸终端、安检门）天然有"技术门槛"：面部术后、轮椅、听力障碍、
植入医疗器械、少数民族证件格式……这些考生如果只能走智能通道，就会**因为设备而进不了考场**。
本模块把"必须留一条人工路"变成系统里跑得起来的东西：

| 环节 | 系统里怎么落地 |
| --- | --- |
| 三通道并行 | 通道台账按考点登记"智能 / 人工 / 无障碍"三类，逐条做合规校验（净宽 ≥900mm、回转 ≥1500mm、低位终端 ≤1100mm 且高度可调、语音+文字双提示），算**无障碍通道配置率** |
| 特殊考生档案 | 按需求类型（面部特征异常/视力/肢体/听力/医疗/语言/认知）建档，**自动推荐保障措施**，逐项记录"申请→审批→落实（责任人+位置）" |
| 单独同意 | 未取得单独同意的考生**不采集人脸**，自动安排人工核验通道；**任何情况下不因设备拒绝入场** |
| 替代核验 | 人工核验 + **双证比对**（≥2 项一致且必须含身份证/准考证/护照）+ **双人见证**（见证人≠主检人），结论与智能核验**同等效力**（写进代码与报告） |
| 因技术原因受阻 | 每次因设备/算法/画质原因启用人工核验，都登记一条受阻事件并尽量闭环到"已入场"；`未能入场` 单独计数（指标要求 **0 起**，有则原样列出） |
| 算法公平性 | 按性别/年龄/眼镜/口罩/遮挡/肤色分层录入样本与通过数，算**组间通过率最大差**，超差必须记录补偿策略（调阈值/补样本重训/该分层优先人工核验）并复测留痕 |
| 演练 | 每考期 ≥1 次，演练记录必须写"发现了什么问题 + 怎么整改"，否则系统拒绝保存；替代通道可用性按考期统计 |

## 二、关键指标（与文档第三节同一口径）

| 指标 | 要求 | 系统口径 |
| --- | --- | --- |
| 无障碍通道配置率 | 100% 考点 | `settings.sites` 为分母；该考点三类通道都有**可用**的、且无障碍通道校验无 error |
| 替代核验通道可用性 | 100%，每考期 ≥1 次演练 | 每考点有可用的人工/无障碍通道 **且** 本考期演练 ≥1 次、无不合格演练 |
| 因技术原因未能入场 | 0 起 | 受阻事件的结案类型 = `denied` 的条数 |
| 算法分层测试 | 覆盖主要分层，差异可接受 | 最近一次测试覆盖性别/年龄/眼镜/口罩，且组间最大差 ≤5% |
| 保障措施落实率（过程） | ≥95% | 推荐措施中状态为"已落实"的比例 |
| 替代核验及时率（过程） | 3 分钟内完成 | 未超过 `ALT_VERIFY_SLA_SEC` 的比例 |
| 受阻事件闭环率（过程） | 100% | 受阻事件已结案比例 |

界面「概览」页与验收报告用**同一套** `metrics.compute()`，所以报告里的数字与界面永远一致。

## 三、与其它专题的联动（只读调用，不改它们一行）

本模块的硬约束：**只修改 09 目录，不改 00/01/02/03/06 的任何文件**。联动这样实现：

```
                 ┌──────────────── 00_集成联动 · linkage.py（子进程 + JSON 总线）────────────────┐
                 │  ① 09 在**内存里**把自己注册进 PROJECTS["09"]（不改 00 的文件）              │
01 人脸 ────────►│  ② 09 -> 01  人脸核验失败/不可用  -> 触发替代核验（人工兜底）                │
02 摄像头 ──────►│  ③ 02 -> 09  机位画质可信度低     -> 核验结论降权、优先人工核验             │
03 智能终端 ◄────│  ④ 09 -> 03  受阻事件（红）/ 启用替代核验（橙）推送 + 复核结案留痕           │
06 智能安检 ────►│  ⑤ 06 -> 03  特殊考生人工安检通道（同一个告警码 SECURITY_SPECIAL_CHANNEL）  │
                 │     09 只读 03 的告警与 06 的概览，用来和本模块档案**对账**                  │
                 └──────────────────────────────────────────────────────────────────────────────┘
```

具体接口（`linkage_bridge.py`）：

| 函数 | 走向 | 说明 |
| --- | --- | --- |
| `register_self()` | 09 → 00 | 内存注册（`PROJECTS["09"]`），于是 09 也能被同一条总线调用 |
| `self_status()` | 09 → 00 → 09 | **经总线调自己**，证明协议完全一致（自检里真跑一次） |
| `face_verify()` / `candidate_roster()` | 09 → 01 | 人脸核验 / 已建档考生；01 不可用时**如实返回**，不抛异常 |
| `camera_credibility()` | 09 → 02 | 机位画质可信度；低可信度时替代核验优先 |
| `notify(code, info)` | 09 → 00 → 03 | 推送告警：**显式带级别**（09 的码不在 03 的码表里，不修改 03 的前提下这是既有能力），失败退 03 已注册等价码，再失败进 `outbox` |
| `list_alerts()` / `close_alert()` | 09 ↔ 03 | 查告警 / 复核结案；**红色预警要求 03 终端先人工确认**，09 如实返回"需人工确认"而不绕过 |
| `security_status()` / `special_channel_alerts()` | 09 ↔ 06/03 | 与 06 的人工安检通道对账 |
| `flush_outbox()` | 09 → 03 | 03 不可达时事件进本地队列，恢复后补发（**事件不丢**） |
| `probe()` | 全链路 | 一键探测，界面/自检/命令行共用 |

**反向调用（别的专题怎么调 09）** —— 两种方式，都不需要改任何人的代码：

```python
# 方式一（推荐，零依赖）：按同一套协议起子进程
#   python <All>\09_无障碍与特殊考生保障\integration_api.py --op status --args "{}"
# 方式二：用 00 的总线句柄（先让 09 在内存里注册）
import sys; sys.path.insert(0, r"...\09_无障碍与特殊考生保障")
import linkage_bridge; linkage_bridge.register_self()
import linkage; linkage.Project("09").call("status", {})
```

**两个刻意的设计选择**（写下来免得后人误解）：

1. 09 的告警都是**现场人工确认**后发出的（考生就站在通道口），所以默认**不参与** 02 的
   "画质可信度降权"（避免真事故被当成画质误报压成橙色），但会把当时的画质可信度写进告警详情；
   只有自动触发型通知（`human_confirmed=False`）才降权。
2. 红色告警在 03 里必须**先人工确认再复核**，这个确认动作只在 03 界面做（集成接口没有该 op）。
   09 不去绕过它 —— 这恰恰是"防一键消警"的控制点，自检里专门有一条断言守着这个行为。

```
[1] 配置与字典        指标口径、需求/措施/通道/告警码字典、设置读写、掩码脱敏
[2] 存储与加密        建表、字段白名单、盲索引、敏感字段加密落库、审计哈希链与篡改检测
[3] 通道与合规        净宽/回转/低位终端/双提示校验、降级可用约束、三通道并行、配置率 100%
```

第 [10] 组是**真的跨进程跨模块**跑的（02/03/06 的数据目录被重定向到临时目录，不污染它们的真实数据），
第 [11] 组会把 00/01/02/03/06 关键文件的 SHA-256 指纹在自检前后对比，**用证据说明"只改了 09"**。

## 七、如实说明

1. **通道尺寸是现场实测录入值**：净宽/回转/台面高度/提示方式由现场测量与验收填写，
   系统只做合规判定，不推算、不代填。
2. **没有真实设备时用演示数据**：来源标 `demo`，界面与报告都会写明"演示"，不冒充真实保障记录。
3. **01 人脸核验在本机可能不可用**（特征索引未建），此时替代核验流程照常走通 ——
   这正是本专题要演示的场景：**算法不可用不等于考生不能入场**。
4. **未取得单独同意**的考生一律走人工核验通道，不采集人脸；本模块从不以"未同意"为由拒绝入场。
5. **加密**：装了 `cryptography` 则考生标识/医疗证明编号/联系方式加密落库（`enc:` 前缀）并配盲索引；
   没装则如实降级为明文并在界面/报告里写明。密钥优先取环境变量 `EXAM_DATA_KEY`，否则用 `data\.data_key`。
