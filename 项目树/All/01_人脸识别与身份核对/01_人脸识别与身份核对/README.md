# 人脸识别与身份核对（01）

智能考场 AI 巡考系统 · 项目六 专题 01。本目录是**可运行的原型**：报名库 → 特征建档 →
摄像头抓拍 → 身份要素 + 人脸核验 → 分级结论 → 审计留痕，另附网页端考生数据管理与用户权限。

> **本次改造（两个所有者开关）**：新增「**大考模式**」（默认关闭）与「**严格模式**」（默认开启）。
> 大考模式决定身份证是否必须校验（四要素 / 三要素，见第三节），严格模式决定能否用本地图片核验。
> 两者都可在 GUI「操作记录 → 所有者设置」与网页端「⚙ 所有者设置」里切换，切换动作写审计。

## 一、5 分钟跑起来

```bat
:: 0) 环境（Python 3.11/3.12）
pip install -r requirements-face.txt

:: 1) 初始化/迁移数据库（自动把旧库里明文身份证号转成加盐哈希 + 掩码）
python 网页操作面板\server\db.py

:: 2) 导入旧 JSON 报名库（可选，仅首次迁移用）
python enroll.py migrate-json

:: 3) 提取人脸特征，生成加密索引，随后删除原始参考照（合规要求）
python enroll.py build --purge-photos

:: 4) 自检（真实模型，含"他人照片冒充必须拦截"的回归断言）
python main.py

:: 5) 打开图形界面
start_gui(打开图形化界面).bat
```

网页操作面板：

```bat
python 网页操作面板\server\db.py            :: 首次会生成随机初始密码
python 网页操作面板\server\启动后端.bat      :: 浏览器访问 http://127.0.0.1:5000
```

> 初始密码为**随机生成**，见 `网页操作面板/server/初始密码.txt`；管理员改密后该文件自动删除。
> 若历史库用过默认口令 `Admin@123`，执行 `python 网页操作面板\server\db.py --reset-admin` 重置。

## 三、关键设计（与旧版的差异）
| 主题 | 旧版做法 | 现版本 |
| --- | --- | --- |
| 相似度口径 | `(cos+1)/2` 映射后再套 0.65 阈值，等效原始余弦 0.30 就放行 | **直接用原始余弦**，1:1=0.55、1:N=0.65（可环境变量覆盖） |
| 1:N 性能 | 对每个考生重新读图、检测、提特征（N 次推理） | 建档时预提特征，检索为**一次矩阵点积** |
| 参考照 | 原始人脸照片明文存盘 | **只存加密特征索引**，`--purge-photos` 删除原图 |
| 身份证号 | 明文存在 JSON/SQLite/日志 | 加盐哈希 + 掩码，接口不下发明文，迁移后 `VACUUM` 清除物理残留 |
| 数据源 | GUI 读 `candidates.json`，网页写 `exam.db`（两套数据） | 统一为 SQLite 单一数据源 |
| 身份证的要求 | 一律必须校验身份证，无身份证的考生**无法核验**；界面却把这组校验叫作"四要素" | **条件必填**：大考模式开启才必须身份证（四要素）；默认关闭时身份证不参与校验，用准考证号核验（三要素） |
| 证件不符 | 被改写成"转人工"（等于放行路径） | 硬失败直接 FAIL，**不降级、不重试** |
| 现场性 | 传参考照当现场照也能 PASS | 严格模式要求**设备实时抓拍令牌**，否则拒绝放行；严格模式可由所有者关闭（留痕） |
| 活体 | 无，但对外宣称"防照片/面具" | 明确声明**未实现**，留 `liveness.set_checker()` 接口，严格模式缺活体即拒绝 |
| 审计日志 | 纯文本，改一行无人知 | **哈希链**，`verify_chain()` 可检出任何删改；旧日志自动归档 |
| 网页端密钥 | JWT 默认密钥写死在源码里 | 环境变量优先，否则首次随机生成并持久化 |
| 网页端 CORS | `origins="*"` | 白名单（`ALLOWED_ORIGINS`） |
| 保存考生 | 先 `DELETE` 全表再逐条 `INSERT` | 事务化 UPSERT，任一条非法整批回滚 |
| 默认口令 | `admin/Admin@123` 写在前端与文档里 | 随机初始口令；改密后删除密码文件；**首次登录不再强制改密**，改为顶部横幅提示 |
| 账户禁用 | 旧 token 仍可用 8 小时 | 每次请求回查数据库，禁用即时生效；角色以库为准 |

## 三之二、两个所有者开关与"四要素"的新语义

### 1) 大考模式（`data\major_exam.on`，**默认关闭**）

标记文件**存在 = 开启**（与 `manual_add.on` 等既有开关同向）。它决定**身份证是否参与校验**：

| 模式 | 核验项（界面标题） | 算法实际比对 | 身份证 |
| --- | --- | --- | --- |
| **关闭（默认）** | 三要素（常规模式）：准考证号 + 座位号 + 姓名 | 准考证号、座位号 | **不参与校验**：未登记身份证的考生也能核验；若操作人员填了明文，则仍要求一致（避免"填错也放行"） |
| **开启** | 四要素（大考模式）：身份证号 + 准考证号 + 座位号 + 姓名 | 身份证号（加盐哈希）、准考证号、座位号 | **必填**：必须输入证件原件明文；界面上带出的掩码含 `*`，**不算**提供明文，会被拦截 |

- 准考证号在**两种模式下都是必填项**，留空或不一致一律 `FAIL / TICKET_MISMATCH`；座位号不一致 `FAIL / SEAT_MISMATCH`。
- "姓名"由 `document_info()` 自动带出，供工作人员**目视核对证件实物**，不做字符串比对（库内即同名，自比无意义）。
- 每条核验记录写入 `id_mode`（`major` / `normal`）与 `elements_checked`（本次实际校验了哪几项），
  常规模式下跳过身份证时 `id_check_skipped=True`——**放宽了什么，审计里写得出来**。
- 界面文案随开关变化，**常规模式下不再出现"必须身份证"这类说法**（`accounts.identity_mode_text()` 统一生成）。

**各条核验通道如何遵守（含明确不遵守的边界）**：

| 通道 | 常规模式（默认） | 大考模式 |
| --- | --- | --- |
| GUI「开始核验 / 自动核验」（1:1） | 先校验身份要素（准考证必填） | 先校验身份要素（身份证必填），不填即拦 |
| 网页端 `/api/verify`（1:1） | 同上（请求体带 `id_card`/`ticket_no`/`seat_no`） | 同上；**一个要素都不传也会被拦**（`ID_MISMATCH`） |
| `verify_1to1`（库内调用 / `main.py` 自检） | 校验身份要素 | 校验身份要素 |
| `integration_api.py --op verify`（1:1） | 可选传 `id_card`/`ticket_no`/`seat_no`；不传则只做"人脸 + 现场性" | **必须**传 `id_card` 明文，否则拦 |
| `auto_verify.py --mode 1:1`（无人值守） | 只做"人脸 + 现场性"，**不校验身份要素**（该通道没有输入号码的手段） | **拒绝启动**（退出码 2），避免静默跳过身份证 |
| 1:N 抽查（GUI / 网页端 / `auto_verify.py`） | 1:N 本就不比对身份要素 | 同左 |

> 无论哪条通道，**证件实物核对（`DOC-CHECK`）都仍需人工完成**。

### 2) 严格模式（`data\strict_mode.on`，**默认开启**）

> ⚠️ 这个标记文件的语义是**反向**的，和另外两个开关不同：
> **文件不存在 = 严格模式开启（默认）**；**文件存在 = 严格模式已被所有者关闭**。
> 之所以反向，是因为默认值是"开启"，而默认状态下不应该存在任何标记文件
> （否则全新安装要先写一个文件才能得到默认行为）。

| 状态 | `source="camera"`（实时抓拍） | `source="file"`（本地图片 / 上传照片） |
| --- | --- | --- |
| **开启（默认）** | 令牌在有效期内则继续判定 | **直接拒绝**：`FAIL / LIVENESS_UNAVAILABLE` |
| **关闭** | 同左 | **继续判定**，但记录写入 `strict_mode_off=True`、`strict_mode_off_reason`、`non_live_source="file"`，原因文本以"严格模式已关闭（所有者设置），本次为非现场图片来源…"开头 |

> `strict_mode_off_reason` 区分成因：**所有者关闭了严格模式**（运行时可切）还是
> **部署级 `FACE_REQUIRE_LIVENESS=0`**（部署时决定）——审计不会把责任记错人。

- 关闭严格模式**不会**绕过活体模型显式判 `FAIL` 的情况（`LIVENESS_FAILED` 仍是硬失败）。
- 部署级开关 `config.REQUIRE_LIVENESS`（环境变量 `FACE_REQUIRE_LIVENESS`）仍然是总闸：
  两者同时为真才严格（`FaceVerifier.strict_mode_active()`）。
- GUI 的「选择图片」按钮**只在严格模式关闭时可用**；严格模式开启时按钮文案会变成
  「选择图片（严格模式已禁用）」，点击会弹出明确说明与开启路径，**不是静默失败**。
- 网页端「📁 选择照片核验」同理：严格模式开启时点它直接说明原因，不上传。

切换动作（GUI 与网页端）都会写界面操作日志 + `data_change_log`，谁在什么时候改的开关可追溯。

## 四、异常状态与极端情况处理

判定不再只有"通过/不通过"两档，而是**分级**：先排除"不可信"的情形，再谈分数。

| 情形 | 判定 | 原因码 | 处理要求 |
| --- | --- | --- | --- |
| 相似度达标且明显高于其他人 | PASS | `PASS` | 放行 |
| 相似度落在**灰区**（阈值−灰区宽度 ~ 阈值） | MANUAL | `AMBIGUOUS` | 人工复验（双人见证） |
| 与"最像的另一人"差距 < 撞脸余量（双胞胎/撞脸） | MANUAL | `TWIN_SUSPECT` | 人工复验（双人见证 + 辅助证件） |
| 现场人脸更像库里**另一个**考生 | MANUAL | `IDENTITY_CONFLICT` | 人工复验（双人见证），排查身份混淆 |
| 画质**严重**不足（严重欠曝/严重模糊/人脸极小） | MANUAL | `IMAGE_QUALITY_REVIEW` | 重拍或人工核验，**不下"非本人"结论** |
| 极端视角（仰拍/侧脸/歪头超阈值） | MANUAL | `POSE_EXTREME` | 人工复验（换角度重拍更佳） |
| 画质有告警 + 相似度偏低 | MANUAL | `LOW_SIMILARITY` | 人工复验（双人见证） |
| **画质正常**但相似度显著低于灰区下界 | FAIL | `NOT_MATCHED` | 判定非本人，需人工介入处置 |

要点：

- **不冤枉考生**：只要画质有严重问题或存在姿态极端，就不允许算法下"非本人"的结论——昏暗、仰拍这类
  现场条件下，宁可转人工，也不误判；
- **不放过冒充**：画质正常且分数明显偏低才算 `NOT_MATCHED`；这类记录 `manual_required=True`，
  仍会进入人工处置流程；
- 灰区、撞脸、身份混淆三类都要求 `required_witness=True`：必须双人见证，界面会强制提示填见证人。

### 昏暗与仰拍的专门优化

| 问题 | 手段 |
| --- | --- |
| 光线昏暗 | 先在 **LAB 空间做 CLAHE**（局部对比度）＋**伽马提亮**，再检测/提特征；伽马方向为 `255·(i/255)^0.65`（<1 才是提亮） |
| 失焦/运动模糊 | **非锐化掩模（USM）** 锐化 |
| 暗部噪声 | **双边滤波**（保边去噪） |
| 增强反而更差 | 同时评估"原图"与"增强图"，**取问题更少的那个**（`_better()`），并记录 `enhanced` 标志 |
| 仰拍/侧脸 | 用 5 点关键点估计 yaw/pitch/roll，超阈值即 `POSE_EXTREME` |

> ⚠️ **姿态是近似估计**：由 5 点关键点的几何比例映射而来，用于**触发复验**，不是标定角度，
> 也不作为判定依据。倾斜较大的真实仰拍会被拦下，轻微角度不会误报。
> 实测（`python main.py`）：昏暗照原图亮度 33.6 → 增强后 77.2，相似度 0.8877 → 正常放行。

### 双胞胎提前识别

考前跑一次撞脸体检，提前把长得像的考生挑出来，为他们安排复验流程：

```bat
python enroll.py check-twins                :: 列出库内相似度超阈值（默认 0.45）的考生对
python enroll.py check-twins --threshold 0.6
```

核验时若"本人得分 − 最像者得分 < 撞脸余量（默认 0.08）"，一律转双人见证复验。

## 五、人脸先过、证件后核（证件核对环节）

**流程**：人脸比对通过 → 系统**自动带出**该考生的证件信息 → 工作人员对照证件实物目视核对
→ 点「证件一致」留痕，或点「证件不符」当场拦截。

```
场景11 实测：
带出：姓名 张三 ｜ 准考证 2026T001 ｜ 座位 A-01 ｜ 身份证 3301**********1234
```

**带出什么、为什么只有掩码**：

| 项 | 说明 |
| --- | --- |
| 带出内容 | 姓名 / 准考证号 / 座位号 / **身份证掩码**（`3301**********1234`） |
| 为什么没有明文 | 库里只存 `salt + hash + 掩码`，明文**不可逆**——这是合规设计，不是缺陷 |
| 因此这一环是 | **人工目视核对**证件实物，不是算法比对 |
| 需要严格比对时 | 工作人员在「身份要素校验」里手工输入完整号码 → 走哈希比对（不一致即 `ID_MISMATCH` 拦截）；**大考模式下这一步是必填的** |

**审计留痕**：证件核对**单独写一条记录**（`mode=DOC-CHECK`，原因码 `DOC_CHECK_CONFIRMED`
或 `DOC_MISMATCH`），与人脸记录时间戳相邻、同入哈希链；记录里保存当时展示的
`id_card_display`（掩码），可证明"工作人员看到的是什么"。
> 统计"核验通过率"时只统计 `mode` 为 `1:1` / `1:N` 的记录，避免把证件核对确认也算成一次通过。

### 身份要素的两种输入通道（GUI / 网页端）

| 通道 | 用途 | 是否参与算法比对 |
| --- | --- | --- |
| **身份要素校验** 的核验输入框（准考证号 / 座位号 / 身份证号） | 操作人员填写，点「⇩ 按所选考生带入」可从报名库带出准考证与座位 | **是**（大考模式下身份证必填） |
| **报名库带出（只读）** 的展示行 | 人脸通过后带出掩码等信息供目视核对证件实物 | 否（展示用） |

> 「⇩ 按所选考生带入」**不会**替你填身份证号明文（库里只有哈希，掩码不可反推）；
> 大考模式下必须人工输入证件原件号码。

## 六、边缘计算优化

目标：**在考点边缘节点上跑得动、跑得稳、断网也能跑**，云端只收结构化结论。

### 1) 推理后端自动适配（`edge.detect_providers`）

按优先级探测：TensorRT（Jetson）→ CUDA → **CANN（华为昇腾 Atlas 300V/310/310P）** →
MIGraphX → OpenVINO → CoreML → DirectML → CPU。可用 `FACE_EP` / `FACE_DEVICE` 强制指定，
指定的后端不可用时**明确降级并在记录中留痕**，不静默失败。

```bat
python enroll.py edge-status        :: 看当前生效后端、可用后端、未启用的加速后端
set FACE_EP=cann                    :: 指定昇腾
set FACE_EP=cpu                     :: 强制 CPU（便于对比性能）
```

### 2) 算力自适应降档（`edge.ResourceMonitor`）

实测单次推理耗时，滚动窗口超阈值就自动降档，回落后再升档（带冷却期，避免一次抖动连降两级）：

| 档位 | 检测分辨率 | 限帧 | 低画质增强 | 批大小 |
| --- | --- | --- | --- | --- |
| `full` | 640px | 不限 | 开 | 8 |
| `balanced` | 480px | 8 fps | 开 | 4 |
| `lite` | 320px | 4 fps | **关**（最省算力） | 2 |

降档会真实生效：`face_engine.get_app()` 检测到档位变化会用新的 `det_size` 重新 `prepare`。
记录中带 `edge_profile` / `edge_degraded` / `edge_latency_ms`，事后可解释"当时为什么降档"。

### 3) 多路并发批处理

`FaceIndex.identify_batch(images)` / `extract_batch(images)`：一次处理多路摄像机的帧，
**共用已加载模型与同一份索引矩阵**，单帧失败只置空、不中断整批。

> 说明：insightface 的检测器不接受批量输入，这里的"批量"省掉的是模型重复加载与索引矩阵重复构建；
> 若边缘设备支持批推理，可在 `extract_batch` 内替换为 `recognition.get_feat()` 的批量调用。

### 4) 断网降级 + 只传结构化结果（`edge.Outbox`）

核验记录先落本地 `data\outbox.jsonl`，网络恢复后上报；上报失败**保留在队列**，不丢数据。
上报内容只有结构化字段（考生号/结果/原因码/分数/画质/边缘状态），**不含图像与特征向量**——
既省考点上行带宽，也符合"生物特征不出考点"的合规要求。

```bat
python enroll.py flush-outbox --url http://<云端>/api/verify-records
set EDGE_UPLOAD_URL=http://<云端>/api/verify-records   :: 或配置一次，长期生效
```

### 5) 与端边云三层架构的对应

| 层 | 本模块承担的职责 |
| --- | --- |
| 端（闸机/摄像机） | 采集、现场令牌（证明是实时抓拍） |
| **边（考点服务器/边缘盒子）** | 检测、对齐、提特征、画质与姿态评估、增强、判定、审计哈希链、断网缓存 |
| 云（省级平台） | 汇总统计、阈值下发、模型版本管理（通过 `flush-outbox` 上报结构化结论） |

## 七、阈值标定（上线前必做）

`config.py` 中的 0.55 / 0.65 是 InsightFace 的**一般经验值**，不构成验收依据：

1. 准备同一人的多张照片（不同光照、角度、时间）与不同人的照片；
2. 计算两类相似度分布，取误识率 ≤0.1% 且拒识率 ≤1% 的临界点；
3. 把结果写入 `FACE_THRESHOLD_1TO1` / `FACE_THRESHOLD_1TON`；
4. 变更后重跑 `python main.py` 与 `python -m unittest discover -s tests -t .`。

灰区与撞脸相关参数（都在 `config.py`，可用同名环境变量覆盖）：

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `FACE_GRAY_MARGIN_1TO1` | 0.10 | 灰区宽度：0.45~0.55 之间转人工复验 |
| `FACE_GRAY_MARGIN_1TON` | 0.10 | 1:N 的灰区宽度 |
| `FACE_TWIN_MARGIN` | 0.08 | 与最像者差距小于该值 → 撞脸复验 |
| `FACE_TWIN_ENROLL_WARN` | 0.45 | `check-twins` 的告警阈值 |
| `FACE_QUALITY_MIN_BRIGHTNESS` | 45 | 亮度低于该值告警 |
| `FACE_QUALITY_SEVERE_BRIGHTNESS` | 28 | 低于该值视为严重欠曝 → 复验 |
| `FACE_QUALITY_MIN_SHARPNESS` | 35 | 拉普拉斯方差下限 |
| `FACE_QUALITY_MIN_FACE_RATIO` | 0.06 | 人脸框面积占比下限 |
| `FACE_POSE_MAX_PITCH_UP` | 35 | 仰拍超过该角度 → 复验 |
| `FACE_AUTO_ENHANCE` | 1 | 是否启用低画质自动增强 |
| `FACE_EP` | auto | 推理后端（`cann`/`tensorrt`/`cuda`/`openvino`/`cpu`） |
| `EDGE_PROFILE` | full | 起始边缘档位（`full`/`balanced`/`lite`） |
| `EDGE_UPLOAD_URL` | 空 | 云端接收核验记录的地址 |

> 1:N 的阈值必须严于 1:1（误识率随底库规模放大）；底库规模超过 1000 人时建议重新标定并考虑阈值随 N 自适应。

## 十一、身份证号存储加固与明文清理

### 密钥化 HMAC（数据库被拷走也无法爆破）

哈希格式带 `hmac1:` 前缀：`HMAC-SHA256(密钥, 盐 + 规范化号码)`。

| 手段 | 作用 |
| --- | --- |
| **密钥**（32 字节随机，DPAPI 加密存于 `data/id_key.enc`，与数据库分离） | 只有拿到本机用户身份才能计算，攻击者光有 `exam.db` 无法离线爆破 |
| **每人独立随机盐** | 同一号码在不同记录中哈希不同，无法跨记录关联比对 |
| `hmac.compare_digest` | 等值比对用常数时间比较，避免时序侧信道 |
| 旧数据兼容 | 无 `hmac1:` 前缀的旧记录继续按 `salt + SHA-256` 校验，登录/核验不受影响 |

> 为什么必须改：身份证号可猜空间约 10^11（地区码×生日×顺序号），单次 SHA-256 在 GPU 上几秒就能穷举完。
> 换机器后 `id_key.enc` 无法解密 → 该记录判"不通过"（需重新登记），这是预期的安全行为。

### 明文残留清理

旧版把明文身份证号写在 `candidates.json`，日志里还会带出以身份证号命名的照片路径。
新版已改为哈希存储 + 写日志前脱敏，但历史文件里的明文仍在磁盘上，用一条命令清掉：

```bat
python enroll.py scrub-plaintext            :: 预演：扫描数据目录/备份目录/工程目录
python enroll.py scrub-plaintext --apply    :: 执行脱敏（原文件备份为 *.premask.bak）
```

扫描范围：`data\`、`备份\`、工程目录下的 `.log/.json/.txt/.csv/.bak` 等文本文件；
脱敏后自动复查并报告残留。**本次执行结果：已无明文身份证号。**

## 十二、常见问题

**Q：批处理双击闪退，或报"命令語法不正確 / '%i' 不是内部或外部命令 / '功]' 不是内部或外部命令"？**
A：**批处理必须是 CRLF 行尾**，LF（Unix 换行）会让 cmd 把行拆错，典型症状就是标签、`for`、`exit /b` 全乱。
本目录的 `.bat` **已全部统一为 CRLF**。如果你自己改过脚本，请用记事本/VS Code 另存为 CRLF；
也可以跑一次检查：

```bat
powershell -c "Get-ChildItem *.bat -Recurse | ForEach-Object { $b=[IO.File]::ReadAllBytes($_.FullName); $lf=0; for($i=0;$i -lt $b.Length;$i++){ if($b[$i] -eq 10 -and ($i -eq 0 -or $b[$i-1] -ne 13)){$lf++} }; if($lf){ $_.Name + ' 有 ' + $lf + ' 处裸 LF' } }"
```

**Q：双击 .bat 时它挑了错的 Python（提示缺少 numpy / insightface）？**
A：机器上可能装了多个 Python（例如本机有 3.12 与 3.15，默认的是没装依赖的 3.15）。
所有 `.bat` 现在都通过 `pick_python.py` 挑选**真正装了依赖**的解释器，不再猜：

```bat
python pick_python.py face --all     :: 列出全部候选及各自缺什么
python pick_python.py face           :: 直接输出最适合的解释器路径
```

**Q：网页里"导入 Excel / 导出 Excel"点了没反应？**
A：前端依赖 xlsx 库。原版从 jsdelivr CDN 加载，**考场内网/教育专网通常访问不了**，
所以已把库本地化：`网页操作面板\vendor\xlsx.full.min.js`（882KB，随项目分发），
本地缺失时才回退 CDN；两者都没有会弹出明确提示。

**Q：打开 http://127.0.0.1:5000/ 显示 404？**
A：旧版 `app.py` 里 `HTML_DIR` 多拼了一层目录（`server\..\网页操作面板`），首页一直打不开。
已修正为 `server\..`，并新增 `/vendor/...` 静态路由。

**Q：报 `cv2.imread` 读不到图 / 返回 None？**
A：Windows 下 `cv2.imread` 不支持中文路径。代码已统一改用
`face_engine.imread_unicode`（`np.fromfile` + `cv2.imdecode`）。自己写脚本时请沿用该函数。

**Q：`insightface` 报找不到模型？**
A：把 `buffalo_l.zip` 解压到 `%USERPROFILE%\.insightface\models\buffalo_l\`
（含 `det_10g.onnx`、`w600k_r50.onnx` 等），无需改代码。

**Q：为什么严格模式下用"选择图片"核验一定失败？**
A：这是有意设计：文件来源无法证明是现场采集，系统宁可不放行，也不做无法验证的判定。
需要用本地图片核验（离线演示、事后复核）时，**由所有者在「所有者设置」里关闭「严格模式」**
即可立即生效，且每次核验都会在审计里标注"严格模式已关闭、本次为非现场图片来源"。
（也仍可用环境变量 `FACE_REQUIRE_LIVENESS=0` 在部署层面整体关掉，不建议。）
严格模式开启时点「选择图片」会弹出说明，**不会静默失败**。

**Q：为什么 `data/candidates.json` 被删了？**
A：它是旧版的明文报名库，已迁移进 SQLite（身份证号转为加盐哈希）。原件保留在
`../../_backup/01_人脸识别与身份核对_修改前_*/data/candidates.json`。
