## 二、两个开关：大考模式 / 严格模式

两个开关都**只归所有者**，在 GUI 与网页端各有一个入口，切换**立即生效、无需重启**，
且切换动作会写入界面操作日志与 `data_change_log`。

| 开关 | 界面入口 | 标记文件 | 默认值 |
| --- | --- | --- | --- |
| **大考模式（必须使用身份证）** | GUI：更多操作 → 操作记录 → 所有者设置；网页端：侧边栏「⚙ 所有者设置」 | `data\major_exam.on` | **关闭** |
| **严格模式（关闭后可选本地图片核验）** | 同上 | `data\strict_mode.on` | **开启** |

### 标记文件语义（重要，两者方向不同）

| 开关 | 文件**存在** | 文件**不存在** |
| --- | --- | --- |
| 大考模式 | 大考模式**开启**（必须身份证） | 大考模式**关闭**（默认） |
| 严格模式 | 严格模式**已关闭**（宽松，允许本地图片） | 严格模式**开启**（默认） |

> ⚠️ `strict_mode.on` 的语义是**反向**的：它是"宽松模式"的标记。
> 原因：严格模式的默认值是"开启"，而默认状态下不应该存在任何标记文件，
> 否则全新安装要先写一个文件才能得到默认行为。
> 代码里对应 `accounts.strict_mode_enabled()`（文件不存在 → True）与
> `accounts.strict_mode_relaxed()`（文件存在 → True）。

### 命令行等价操作（不改界面也能切）

```bat
:: 打开大考模式（必须使用身份证）
echo 1> data\major_exam.on
:: 关闭大考模式（回到默认：以准考证号核验）
del data\major_exam.on

:: 关闭严格模式（允许本地图片核验，会留痕）
echo 1> data\strict_mode.on
:: 恢复严格模式（默认）
del data\strict_mode.on
```

> 数据目录被 `EXAM_HOME` 或 `exam_home.txt` 改到别处时，标记文件也跟着去那个数据目录。

## 三、"四要素"在新语义下怎么算

**"四要素"不再是固定说法**，它随大考模式变化；界面标题由
`accounts.identity_mode_title()` 统一生成，不会出现"必须身份证"这类误导文案。

| 大考模式 | 界面标题 | 核验项 | 算法实际比对 | 身份证 |
| --- | --- | --- | --- | --- |
| **关闭（默认）** | 三要素（常规模式） | 准考证号 + 座位号 + 姓名 | 准考证号、座位号 | **不参与校验**。未登记身份证的考生**也能核验**；若操作人员填了身份证明文，则仍要求一致（避免"填错也放行"） |
| **开启** | 四要素（大考模式） | 身份证号 + 准考证号 + 座位号 + 姓名 | 身份证号（加盐哈希）、准考证号、座位号 | **必填**。必须输入证件原件**明文**；界面上带出的掩码（含 `*`）不算提供明文，会被拦截 |

要点：

- **准考证号在两种模式下都是必填项**：留空或不一致 → `FAIL / TICKET_MISMATCH`。
- 座位号不一致 → `FAIL / SEAT_MISMATCH`。
- **姓名**由系统带出，供工作人员**目视核对证件实物**，不做字符串比对（库内即同名，自比无意义）。
- 每条核验记录都会写入 `id_mode`（`major` / `normal`）与 `elements_checked`（本次校验了哪几项）；
  常规模式下跳过身份证时 `id_check_skipped=True`——**放宽了什么，审计里查得到**。

### GUI：两个输入通道别搞混

```
身份要素校验
  三要素（常规模式）：准考证号 + 座位号 + 姓名          ← 标题随开关变
  身份证号[____] 准考证号[____] 座位号[____] [⇩ 按所选考生带入]   ← 核验输入（参与算法比对）
  ─────────────────────────────────────────────
  报名库带出（只读）：身份证号[3301**********1234] 准考证[..] 座位[..]  ← 展示用（供目视核对证件）
```

- **核验输入框**里填的东西才会被拿去比对；1:1 模式下点「开始核验」会先校验身份要素，
  不一致直接拦截并留痕。
- 「⇩ 按所选考生带入」只带**准考证号 / 座位号**；**不会**替你填身份证号明文
  （库里只有哈希，掩码不可反推）。大考模式下必须人工输入证件原件号码。
- 人脸通过后，系统把该考生的证件信息（含身份证掩码）带到**只读展示行**，请对照证件实物
  点「✓ 证件一致」或「✗ 证件不符」（单独写一条 `DOC-CHECK` 审计记录）。

### 网页端

- 「🎥 实时核验」面板里有同样的三个输入框与「⇩ 按所选考生带入」按钮；1:N 抽查不比对身份要素。
- 页面顶部的蓝色提示条会**实时显示当前是几要素、身份证是否参与校验**。

### 哪些通道会遵守、哪些不遵守（边界要说清）

| 通道 | 常规模式（默认） | 大考模式 |
| --- | --- | --- |
| 核验界面（GUI）1:1 / 自动核验 | 校验身份要素（准考证必填） | 校验身份要素（身份证必填） |
| 网页端「🎥 实时核验」1:1 | 同左 | 同左；请求里一个要素都不带也会被拦 |
| `auto_verify.py --mode 1:1`（无人值守） | **只做人脸 + 现场性，不校验身份要素**（该通道没有输入号码的手段） | **拒绝启动**（退出码 2），避免"自动放行却跳过身份证" |
| 1:N 抽查（GUI / 网页端 / `auto_verify.py`） | 1:N 本就不比对身份要素 | 同左 |
| `integration_api.py --op verify`（联动层） | 可选传 `id_card` / `ticket_no` / `seat_no` | **必须**传 `id_card` 明文，否则拦 |

> 无论哪条通道，**证件实物核对（`DOC-CHECK`）都仍需人工完成**。

## 四、严格模式与"选择图片"

| 严格模式 | 摄像头实时抓拍（source=camera） | 本地图片 / 上传照片（source=file） |
| --- | --- | --- |
| **开启（默认）** | 令牌在有效期内即继续判定 | **直接拒绝**：`FAIL / LIVENESS_UNAVAILABLE` |
| **关闭** | 同左 | **继续判定**，但记录写入 `strict_mode_off=True`、`strict_mode_off_reason`、`non_live_source="file"`，原因以"严格模式已关闭（所有者设置），本次为非现场图片来源…"开头 |

> `strict_mode_off_reason` 会区分成因：**所有者关闭了严格模式**（运行时可切）
> 还是**部署级 `FACE_REQUIRE_LIVENESS=0`**（部署时决定）——审计不会把责任记错人。

- GUI：「选择图片」按钮**只在严格模式关闭时可用**。严格模式开启时按钮文案会变成
  **「选择图片（严格模式已禁用）」**，点击会弹出明确说明与开启路径——**不是静默失败**。
- 网页端：「📁 选择照片核验」同理，严格模式开启时点它直接说明原因，**不上传**。
- **关闭严格模式不会绕过活体模型显式判 `FAIL`** 的情况（`LIVENESS_FAILED` 仍是硬失败）。
- 部署级总闸 `config.REQUIRE_LIVENESS`（环境变量 `FACE_REQUIRE_LIVENESS`）仍然有效：
  **两者同时为真**才算严格模式（`FaceVerifier.strict_mode_active()`）。

> 关闭严格模式是**有意留下的运维口子**（离线演示、事后复核），代价是这批结论的证明力下降；
> 因此系统选择"放行但大声留痕"，而不是"悄悄放宽"。

## 五、初始口令：只提示，不强制

- **网页端**：`/api/login` 与 `/api/me` 仍然返回 `must_change_password`，但前端**不再弹窗拦截**。
  登录（或带 token 恢复会话）后直接进入系统，页面顶部出现一条温和横幅：
  「🔑 当前账户仍在使用初始口令，**建议尽快修改**」+「去修改」/「知道了」。
  点「去修改」才打开改密窗口，随时可以关掉。改密成功后横幅自动消失。
- **桌面端**：登录后弹一次 `showwarning` 提示，同样是提示式，不拦截。
- `/api/change-password` 行为不变：改密后删除服务端 `初始密码.txt`；
  所有者重置某账户口令后仍会置 `must_change_password=1`——它现在是"建议"，不是"门禁"。

## 九、命令控制台（默认关闭，权限分两级）

这是一个**有意开放的后门**，用于现场排障与 AI 辅助判断。默认关闭，分两级：

| 角色 | 层级 | 能做什么 |
| --- | --- | --- |
| 所有者 owner | `full` | 任意系统命令 + Python 代码 |
| 管理员 admin | `ollama` | **仅** `ollama run <模型> [提示词]` |
| 教师 / 其他 | `none` | 无入口（也读不到状态接口） |

### 怎么开

1. **所有者**在「更多操作 → 操作记录 → 所有者设置」勾选「命令控制台」
   （网页端在 `⚙ 所有者设置`）；
2. 如需给管理员，再勾选「允许管理员使用「AI 辅助判断」（仅 ollama）」；
3. 开启后入口出现在**实时视频区右侧**（网页端为左侧导航「⌨ 命令控制台」）。

标记文件（删掉即关闭，语义与 `manual_add.on` 一致）：

- `data\cmd_console.on` —— 总开关（关掉则连管理员一并停用）
- `data\cmd_console_admin.on` —— 授权管理员，以总开关开启为前提

### 两级之间靠什么隔开

**白名单整条匹配**，不是"过滤危险字符"：只有 `ollama run <模型> [提示词]` 这一种形式能通过；
模型名限定 `[A-Za-z0-9._:-]` 且不得以 `-` 开头（防注入参数）。
匹配成功后**不走 shell**，模型名与提示词作为独立 argv 交给 ollama 进程——
所以提示词里出现 `|` `&` `>` `;` 换行等字符完全无效，它们只会作为普通文本传给大模型。

`python -m unittest tests.test_cmd_console` 用对抗性输入锁住了这些性质，其中
"元字符必须落在同一个 argv 元素里"是一条防回归断言：若有人把执行改成 `shell=True`，
测试会立刻失败。

### 要清楚的风险

- 所有者层级等价于**本机完全控制权**：能执行命令就能读写考生生物特征库、改程序、装后门。
- 审计哈希链只能"事后可查"，**不能阻止执行**。
- 出厂默认所有者口令已随公开仓库公开（见 `accounts.py` 的 `DEFAULT_ACCOUNTS`），
  **部署前必须改掉**，否则开启本功能等于把机器交出去。
- 网页端默认只监听 `127.0.0.1`；需要局域网访问时设环境变量 `HOST=0.0.0.0`
  ——那会同时暴露整个面板（含考生数据接口），请自行评估网络可信度。

### 已知遗留问题（与本次改动无关）

`data\audit.log` **第 53 行存在一个历史断链**：2026-10-10 有两处并发写入，
两个 `AuditLogger` 实例各自缓存链尾（`self._tail`）导致链分叉。
`audit.py` 没有文件锁，因此 `/api/status` 的「审计链」会显示为不完整。
修复需要给"读链尾 + 追加"加锁；本次未改动该共享代码。
